# Lecciones aprendidas

## [2026-07-24] — `useCdn: true` en build time sirve contenido cacheado y stale
**Contexto:** Cargar contenido real en Sanity (`npm run sanity:seed`) y hacer build para verlo reflejado en el sitio.
**Error cometido:** `sanityClient` (usado tanto en runtime como en build time) tenía `useCdn: true`. Se sembró contenido real y se corrió `npm run build` inmediatamente — el HTML resultante mostraba el fallback vacío para hero/problema/specs/testimonios, pero **sí** mostraba el contenido real de FAQ. Se esperó ~1 minuto extra y se corrió build de nuevo: mismo resultado, contenido vacío persistente en esos mismos tipos.
**Por qué pasó:** La CDN de Sanity cachea por query exacta. Esas queries específicas (`*[_type == "hero"][0]`, etc.) ya se habían pedido muchas veces durante Build 2 (cuando el dataset estaba vacío), y quedaron cacheadas como "sin resultado" con un TTL propio por query — independiente de cuándo se sembró el contenido real. La query de `faqItem` (con `| order(order asc)`, nunca pedida antes con ese filtro) no tenía ese cache viejo, por eso sí mostraba datos frescos.
**Consecuencia evitada:** Publicar contenido nuevo en Sanity y que el sitio siguiera mostrando el estado vacío anterior de forma intermitente e impredecible (algunos bloques actualizados, otros no) — un bug muy difícil de diagnosticar en producción porque "a veces funciona".
**Corrección:** Cambiado a `useCdn: false` en `src/lib/adapters/sanity.ts`. Es la elección correcta para este caso de uso específico: el sitio es estático y el **rebuild ES el mecanismo de refresco de contenido** (Build 3: webhook Sanity → Vercel) — no tiene sentido que ese build, cuya única razón de ser es traer el contenido más nuevo, sirva una copia cacheada. La CDN sí tendría sentido para fetches en el navegador o SSR por-request donde la latencia importa más que la frescura al segundo.
**Regla para el futuro:** Si un fetch de contenido ocurre en un proceso de build/rebuild disparado específicamente porque el contenido cambió, `useCdn: false` (o el equivalente en cualquier CMS headless) casi siempre es lo correcto — la CDN optimiza para reducir latencia en fetches frecuentes, no para garantizar frescura en un evento puntual de "traé lo último ahora".

## [2026-07-24] — Script de GTM con valor dinámico interpolado: Astro no puede hashearlo para CSP
**Contexto:** Conectar un container real de GTM (`GTM-M8VDGDMF`) y correr Lighthouse contra el sitio con GTM activo.
**Error cometido:** El snippet de GTM se escribió como `<script set:html={\`...${containerId}...\`} />` — el `containerId` real interpolado directo en el string del script. Esto es exactamente el patrón que ya había roto la hidratación del formulario (ver la lección de abajo, mismo día): un `<script>` con `set:html` (o cualquier atributo) queda "sin procesar" para Astro, y el mecanismo de hash automático de `security.csp` solo cubre scripts que Astro efectivamente procesa. El resultado: el navegador bloqueaba el script de GTM completo por CSP.
**Consecuencia evitada:** Conectar un container de GTM real y que nunca cargara en producción — exactamente el mismo tipo de bug silencioso (se ve bien en el HTML, no hace nada) que ya había pasado con el formulario, ahora en una feature distinta.
**Corrección:** Separar dato de lógica: el `containerId` se pasa por un atributo `data-container-id` en un `<div>` (markup puro, no sujeto a reglas de CSP de scripts), y el `<script>` que lo lee queda 100% estático — sin `set:html`, sin variables server-side interpoladas — por lo que Astro sí lo hashea automáticamente, igual que los demás scripts inline del sitio.
**Regla para el futuro:** Con CSP estricta + hashes automáticos de Astro: **nunca** usar `set:html` (ni ningún atributo que fuerce `is:inline`) en un `<script>` cuyo contenido dependa de una variable de build/server — separar siempre el valor dinámico (vía `data-*`, `<meta>`, o similar) de la lógica del script, que debe quedar estática para que Astro pueda procesarla y hashearla. Este es el segundo bug de este mismo tipo en la misma sesión — vale la pena grepear el proyecto por `set:html` cada vez que se toque algo relacionado a CSP.
**Tags:** #seguridad #arquitectura

## [2026-07-24] — El formulario nunca se había probado en un navegador real: CSP rompía la hidratación
**Contexto:** Configurar Lighthouse CI y correrlo de verdad (no solo escribir la config) contra el build real.
**Error cometido:** Toda la verificación de `/api/waitlist` durante Build 2 se hizo con `curl` directo al endpoint — nunca se cargó `index.astro` en un navegador real. `curl` no ejecuta CSP (no es un navegador), así que un bug real en la CSP quedó invisible durante toda esa verificación "exhaustiva".
**El bug:** `script-src` no incluía `'self'`. El hash automático que genera `security.csp` de Astro solo cubre `<script>` **inline**; los chunks JS que Astro empaqueta para hidratar el island de React (`WaitlistForm`) se cargan como `<script type="module" src="...">` **externo**, del mismo origen — sin `'self'` (ni un hash, que tampoco aplicaría a un archivo externo), el navegador los bloqueaba. Efecto real: el formulario se veía perfecto en el HTML servido, pero **nunca hidrataba** — ningún click ni submit habría funcionado en producción.
**Segundo bug relacionado:** el honeypot usaba un `style={{...}}` inline de React. Un atributo `style=""` cae bajo la sub-directiva `style-src-attr`, que los hashes de `<style>` de Astro no cubren — también bloqueado.
**Consecuencia evitada:** Shippear un formulario de captación (el corazón del SRS, RF-001) que se ve bien pero no hace nada, detectado recién si un usuario real lo probaba en producción — el peor lugar posible para encontrarlo.
**Corrección:** Se agregó `'self'` a `scriptDirective.resources` en `astro.config.mjs`. Se cambió el `style` inline del honeypot por una clase CSS (`.visually-hidden` en un `<style is:global>`, que si Astro procesa y hashea). Se corrió Lighthouse de nuevo contra el build real y se confirmó "0 errores de consola relacionados a CSP" antes de dar por cerrado.
**Regla para el futuro:** Un endpoint HTTP que funciona por `curl` no prueba que la página que lo consume funciona en un navegador — CSP, hidratación de JS, y errores de consola solo se ven ejecutando el HTML real en un motor de navegador (Lighthouse, Playwright con `page.goto()`, o el navegador a mano). Para cualquier feature con CSP estricta + framework con islands, correr al menos un audit de consola en un navegador real antes de considerarlo verificado.
**Tags:** #seguridad #testing #arquitectura

## [2026-07-24] — Clave de prueba de Turnstile mal transcrita: verificar contra la API real, no solo "se ve bien"
**Contexto:** Con credenciales reales de Resend/Upstash ya conectadas, correr el E2E de flujo completo seguía fallando con `turnstile_failed`.
**Error cometido:** Al documentar en Build 2 las claves de prueba públicas de Cloudflare (`tasks/lessons.md`/`.env`), transcribí el secret key con 3 ceros de menos: `1x0000000000000000000000000000AA` (32 caracteres) en vez del real `1x0000000000000000000000000000000AA` (35 caracteres). Nadie lo notó porque "parece" el mismo patrón de ceros a simple vista.
**Consecuencia:** El endpoint de `siteverify` de Cloudflare respondía `invalid-input-secret` — no `success:false` por token inválido, sino un secret que ni siquiera es un formato reconocido. El flujo de waitlist fallaba en el paso de Turnstile pese a que honeypot, rate limit, Neon y Resend ya estaban bien.
**Corrección:** Se hizo un `WebFetch` a la documentación oficial de Cloudflare para copiar el valor exacto (en vez de confiar en la memoria), y se verificó con una llamada directa a `https://challenges.cloudflare.com/turnstile/v0/siteverify` antes de volver a correr los tests — `success:true` confirmado por fuera del código de la app, aislando la variable.
**Regla para el futuro:** Una clave de prueba "pública y documentada" igual puede transcribirse mal. Antes de asumir que una credencial de terceros está bien copiada, probarla contra la API real del proveedor de forma aislada (un `curl` directo), no solo contra el flujo completo de la app — así se sabe en qué capa está el problema en segundos en vez de sospechar del código propio primero.

## [2026-07-24] — Rate limit compartido entre corridas manuales y automatizadas en el mismo IP
**Contexto:** Debuguear por qué el test E2E de flujo completo devolvía códigos inesperados durante varias corridas seguidas.
**Error cometido:** Correr múltiples `curl` manuales de debug y suites de Playwright completas seguidas, todas desde la misma IP local — el rate limiter de Upstash (5/10min) no distingue entre "tráfico de test automatizado" y "debugging manual", así que todos los intentos del día comparten el mismo balde.
**Consecuencia:** Resultados de test que parecían inconsistentes/flaky (a veces 200, a veces 429 sin cambiar código), lo que podría haberse malinterpretado como un bug en el rate limiter cuando en realidad el rate limiter estaba haciendo exactamente lo que debía.
**Corrección:** Antes de reintentar un test bloqueado por rate limit, borrar la clave específica en Upstash vía su REST API (`GET /keys/waitlist-rate-limit*` → `GET /del/<key>`) para arrancar de un estado limpio y aislar la variable bajo prueba.
**Regla para el futuro:** Al debuguear un endpoint con rate limiting real (no mockeado) desde un entorno de desarrollo compartido, tener en cuenta que TODOS los intentos —manuales y automatizados— consumen el mismo cupo. Si los resultados parecen inconsistentes, verificar primero el estado del rate limiter antes de sospechar de la lógica de negocio.
**Tags:** #testing

## [2026-07-23] — CSP con nonce no tiene sentido en una página estática prerenderizada
**Contexto:** Build 5 (parcial), implementación de la CSP del SRS §5, que pide literalmente `script-src 'self' 'nonce-${NONCE}' ...` y `style-src 'self' 'nonce-${NONCE}'`.
**Error que se evitó:** Implementar un middleware que genera un nonce por request y lo mete en el header, sin darse cuenta de que `index.astro` es una página **estática, prerenderizada en build** (SRS §7: "output estático") — un nonce ahí sería el mismo valor fijo en cada respuesta (el HTML ya está generado, no se re-renderiza por request), lo cual no es un nonce real y da una falsa sensación de protección. Además, Astro inyecta sus propios `<script>`/`<style>` inline (runtime de hidratación de islands, estilos scoped) sin ningún nonce — un CSP nonce-only estricto los habría bloqueado, rompiendo el formulario de waitlist y todos los estilos de la página.
**Consecuencia evitada:** Shippear una CSP que, o bien no protege nada real (nonce fijo reusado), o bien rompe el sitio entero (script-src/style-src estrictos sin nonces en el contenido real).
**Corrección:** Se usó la feature nativa `security.csp` de Astro (hashes SHA-256 de cada script/estilo empaquetado, calculados automáticamente en build, entregados vía `<meta>`). Es el mecanismo correcto para contenido cuyo valor exacto ya se conoce en build time. Como `<meta>` no puede llevar `frame-ancestors` (ignorado por el spec de CSP fuera de un header HTTP), ese directive y los demás headers de seguridad (HSTS, X-Content-Type-Options, Referrer-Policy) se agregaron por separado vía `vercel.json`. Documentado explícitamente en `tasks/todo.md` como desviación deliberada del texto literal del SRS, no como CSP "casi igual".
**Regla para el futuro:** Antes de implementar un requisito de seguridad "tal cual dice el documento", verificar que el mecanismo propuesto sea físicamente compatible con la arquitectura real (estático vs. SSR). Si no lo es, no se improvisa una versión rota — se implementa el mecanismo técnicamente correcto y se documenta la desviación con su razón.
**Tags:** #seguridad #arquitectura

## [2026-07-23] — El propio CSP del SRS bloquearía Turnstile, que el mismo SRS exige
**Contexto:** Misma tarea de CSP. El SRS §5 lista `https://challenges.cloudflare.com` en `frame-src` y `connect-src`, pero no en `script-src`.
**Error que se evitó:** Copiar el `script-src` del SRS literal, que habría bloqueado la carga de `https://challenges.cloudflare.com/turnstile/v0/api.js` — el script que el propio RF-001 exige para el anti-bot Turnstile.
**Consecuencia evitada:** Un formulario de waitlist roto en producción por una CSP mal transcrita, con el anti-bot que se supone lo protege siendo la causa.
**Corrección:** Se agregó `https://challenges.cloudflare.com` también a `script-src` (vía `scriptDirective.resources` de Astro), documentado como corrección deliberada en el código y en `tasks/todo.md`.
**Regla para el futuro:** Cuando un documento de spec define una CSP a mano, verificar cada origen externo mencionado en otra sección (integraciones, RFs) contra las 3-4 directivas relevantes (`script-src`, `connect-src`, `frame-src`, `img-src`) — es fácil listar un origen en una sola directiva y olvidar las demás que ese mismo recurso necesita.

## [2026-07-23] — Astro detecta agentes de IA y fuerza `astro dev` a background
**Contexto:** Configurar Playwright para correr E2E contra un servidor local real.
**Error cometido:** Asumir que `astro dev` corre en foreground (bloqueante) por defecto, como indica su propio `--help`. En este entorno, Astro usa el paquete `am-i-vibing` para detectar que corre dentro de un agente de IA y **fuerza modo background automáticamente**, aunque no se pase `--background`. El proceso padre termina casi inmediatamente (delegando a un daemon huérfano), lo que Playwright interpreta como "el proceso del webServer terminó antes de tiempo" y falla el arranque.
**Intento fallido relacionado:** `astro build && astro preview` tampoco sirve como alternativa porque `@astrojs/vercel` explícitamente no soporta el comando `preview`.
**Corrección:** Pasar `ASTRO_DEV_BACKGROUND=1` como env var al comando (`playwright.config.ts` → `webServer.env`), lo que desactiva la autodetección de agente y deja el proceso en foreground, tal como Playwright necesita.
**Regla para el futuro:** Si un comando de un CLI se comporta distinto a lo que dice su `--help` en este entorno, sospechar primero de autodetección de "agente de IA" antes de asumir un bug o una versión distinta. Buscar env vars de override en el propio paquete (`grep -rn "isRunByAgent\|detectAgenticEnvironment"` en `node_modules`) antes de trabajar alrededor del síntoma.
**Tags:** #testing #arquitectura

## [2026-07-23] — `astro.config.mjs` no ve `.env` vía `process.env` directo
**Contexto:** Conectar el proyecto a un `projectId` real de Sanity (`8fwssle4`). `astro.config.mjs` y `sanity.config.ts` leían `process.env.PUBLIC_SANITY_PROJECT_ID` con fallback a `'placeholder'`.
**Error cometido:** Asumir que Astro carga `.env` en `process.env` antes de evaluar `astro.config.mjs`. En los hechos, ese archivo corre en Node plano (antes de que exista contexto de Vite), así que `process.env.PUBLIC_SANITY_PROJECT_ID` daba `undefined` y el build silenciosamente caía al fallback `'placeholder'` — sin error, sin warning.
**Consecuencia:** El build pasaba, `astro check` pasaba, todo "parecía" funcionar, pero el Studio embebido en `/studio` habría quedado apuntando a un proyecto Sanity inexistente en producción. Se detectó solo porque se agregó un `console.error` de debug y se grepeó el bundle final buscando el projectId real.
**Corrección:** En `astro.config.mjs` (Node plano) se usa `loadEnv()` de `vite` para cargar `.env` explícitamente antes de leer las variables. En `sanity.config.ts` (se bundlea vía Vite para el Studio) se cambió a `import.meta.env`, que sí es reemplazado en build time por Vite. `vite` se agregó como devDependency explícita en vez de depender de que quede hoisteada por Astro.
**Regla para el futuro:** Nunca confiar en que "el build pasó" significa "la config real se está usando" cuando hay fallbacks silenciosos (`|| 'placeholder'`). Después de conectar una credencial real, verificar con un grep del valor esperado en el output de build o con una llamada real a la API — no alcanza con que compile.
**Tags:** #arquitectura #testing

## [2026-07-23] — Versión de Astro y Node: seguridad sobre el pin literal del stack
**Contexto:** Build 1, scaffold inicial. CLAUDE.md especifica "Astro 5.x" y "Node.js 20 LTS".
**Error que se evitó:** Instalar Astro 5.x tal como decía el stack literal habría dejado el proyecto en una versión con 8 CVEs de severidad alta sin parchear (XSS en `define:vars`, slots, spread props, view transitions, SSRF en Host header, etc. — `npm audit`, rango `<=7.0.9`). El fix solo existe desde Astro `7.1.0`, que a su vez requiere Node `>=22.12.0`.
**Consecuencia evitada:** Shippear un framework con XSS conocido y explotable en producción, en el mismo PR que se supone establece la "infraestructura base" segura.
**Corrección:** Se instaló Astro `7.1.3` (última versión con `npm audit` limpio) y se subió el `engines.node` del `package.json` a `>=22.12.0`. El Node 20 LTS mencionado en CLAUDE.md queda desactualizado frente a este requisito real.
**Regla para el futuro:** Cuando un requisito de seguridad no negociable (CLAUDE.md §Seguridad) choque con un pin de versión específico del stack, gana la seguridad — pero se documenta la desviación explícitamente (acá y en `tasks/todo.md`), nunca se decide en silencio. Antes de fijar una versión de un framework, correr `npm audit` con esa versión candidata.
**Tags:** #seguridad #arquitectura

## [2026-07-23] — Vulnerabilidades residuales en tooling de Sanity y del adapter de Vercel
**Contexto:** Build 1, instalación de `sanity`, `@sanity/vision`, `@sanity/astro`, `@astrojs/vercel`.
**Error que se evitó:** Perseguir "0 vulnerabilidades" con `npm audit fix --force` de forma ciega, lo que en este caso proponía downgradear `@astrojs/vercel` a `8.0.4` — versión que exige `astro@^5.0.0` y por lo tanto reintroduce el problema de la lección anterior (Astro <7.1.0 con CVEs de XSS activos), a cambio de resolver un ReDoS en `path-to-regexp` que solo es alcanzable desde herramientas de build, no desde el runtime público.
**Consecuencia evitada:** Cambiar una vulnerabilidad de alto impacto y bajo esfuerzo de explotación (XSS reflejado, alcanzable por cualquier visitante) por una de bajo impacto práctico (ReDoS en una utilidad de routing usada solo en build time) — un mal trade-off de seguridad disfrazado de "audit limpio".
**Corrección:** Se aceptaron 11 vulnerabilidades residuales, todas confinadas a dependencias de tooling (`@sanity/cli`, `@sanity/codegen`, `@sanity/import`, `@sanity/migrate` vía `sanity`; `@vercel/routing-utils` vía `@astrojs/vercel`) que el código de este proyecto nunca invoca en runtime. Documentado como bloqueante de seguimiento en `tasks/todo.md`, no oculto.
**Regla para el futuro:** Antes de forzar un downgrade para "limpiar" `npm audit`, leer qué instala el fix propuesto y evaluar si la nueva versión reintroduce un riesgo mayor al que resuelve. Preferir dejar una vulnerabilidad de bajo impacto y bien documentada, sobre reintroducir una de alto impacto por perseguir un output limpio.
**Tags:** #seguridad #deuda-técnica
